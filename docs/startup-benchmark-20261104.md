# 方案 A 原型实测：单文件外壳 + onedir 落地缓存

测量日期 2026-11-04，同一台机器、同一时段（10:05–10:55），市电供电（台式机无电池），Defender 未安装（详见 §1）。未改动 `dist\DufsGui-v1.6.4.exe`、`DufsGui.spec`、`build.bat`；原型全部在 `_exp\`。

> 这份记录回答什么问题：发布包为什么选择「单文件外壳 + onedir 落地缓存」（方案 A），而不是继续用一次性 onefile，或直接把裸 onedir 目录发给用户。
> 文中「onefile（现状）」指测量时的 v1.6.4；后续发布已按 A 的外壳 + payload 管线落地。

---

## 0. 结论

**A 赢，但只赢在"缓存已经落地"的启动；第一次启动不赢。**

| 指标 | onefile（现状） | A 冷启动 | A 热启动 | 裸 onedir（温） |
|---|---|---|---|---|
| 到窗口可见（5 次中位） | 1,837 ms | 1,833 ms | **329 ms** | 307 ms |
| 相对 onefile | — | −4 ms（−0.2%） | **−1,508 ms（−82%，5.6×）** | −1,530 ms |
| 相对裸 onedir | — | 慢 1,526 ms | +22 ms（+7%） | — |

- **热启动收益成立且很大**：1,837 → 329 ms，省 1.5 s/次；相对裸 onedir 只多 22 ms（外壳读 payload 5 ms + 校验 1,002 个文件 15 ms + 拉起 7 ms）。
- **冷启动没有收益**：1,833 vs 1,837 ms，在噪声内。A 解压出来的仍是 1,002 个全新文件，首次访问的一次性成本照付。
- **"热"能撑住**：受控闲置 5 分钟后复测 A 热 425 / 317 ms、裸 onedir 316 / 286 ms，没有退化。但在 A 热 5 次批次里出现过一次 1,956 ms（实为冷启动——升级测试刚把这个缓存目录删掉了），onedir 也出现过一次 1,864 ms 的单发异常，随后 5 分钟受控闲置复测未再复现（316 / 286 ms）。**该异常未解释，按"偶发后台扫描/预取干扰"记录，不作为稳定属性**；它只说明这台机器上存在 ~1.8 s 级别的背景事件，而 onefile 因为每次都是全新文件，稳定落在这个档位。
- **机制修正**：上一轮"1,013 entry × 1.78 ms ≈ 1.8 s 都花在建文件上"不成立（实测建 1,002 个文件含 33.6 MB 写入只要 269 ms）。这 ~1 s 是"**1,002 个文件第一次被执行/加载**"的成本，典型触发是"文件刚被写入/拷贝"（fresh-copy 首启 1,099–1,808 ms，同目录二启 330 ms）。onefile 每次解压都是新文件所以每次付；A 只在解压那一次付。
- **体积不增反降**：15,660,265 B vs 15,732,766 B（−72,501 B，−0.46%）。
- **代价**：每个版本 35.21 MB 本地缓存（升级瞬间峰值 ~70.4 MB），且首次启动仍 ~1.8 s。
- **Defender 对照做不了**：本机 Defender 未安装、且非管理员，无法加排除。实际在跑的是 QQ 电脑管家文件系统过滤驱动 `QQSysMonX64`。代偿实验（§5）显示"无 Defender 也有 1.5 s 级首访成本"，所以 A 的收益不依赖 Defender；但反过来，"装了 Defender 的机器上 A 是否同样会被扫、收益是否打折"没有实测数据，不作结论。

## 3. 体积与磁盘

| 项 | 字节 | 说明 |
|---|---|---|
| v1.6.4 onefile | 15,732,766 | 现状 |
| **A 分发产物** | **15,660,265** | 外壳 66,048 + payload 15,594,201 + trailer 16 |
| payload（MSZIP） | 15,594,201 | 1,002 个 entry，构建期压缩 3.0 s（含对照用的 zlib 统计） |
| 裸 onedir 目录 | 35,211,658（1,002 文件） | 33.58 MB |
| A 缓存目录（含 marker） | 35,211,751（1,003 文件） | 33.58 MB |
| 升级瞬间峰值 | ~70.4 MB 缓存 + 15.7 MB 分发包 | 保留"当前 + 最近一个" |

压缩算法取舍（同一份 onedir 实测）：

| 算法 | payload 体积 | 解压耗时（外壳内） |
|---|---|---|
| MSZIP（选它） | 15,594,201 B | 166 ms |
| XPRESS-HUFF | 17,475,213 B | 104 ms |
| LZMS | 14,270,376 B | 308 ms |

MSZIP 比 HUFF 小 1.88 MB、只慢 62 ms；比 LZMS 大 1.32 MB、但解压少 142 ms。冷启动一个版本只发生一次，取 MSZIP 作平衡；若更在意下载体积，LZMS 是合理备选（往后再定）。

## 4. 外壳内部耗时拆解

**热启动（缓存命中，单次采样）**

| 标记 | 相对进程启动 |
|---|---|
| payload 读入（15.6 MB） | 6.0 ms |
| payload 解析 | 6.9 ms |
| 路径就绪 | 7.5 ms |
| **缓存命中（含 1,002 次 stat 校验）** | **23.0 ms**（校验 15.2 ms） |
| CreateProcess 完成 | 32.4 ms |
| 外壳进程退出 | 66 ms |
| 窗口可见 | 514 ms（该次偏慢；5 次中位 329） |

**冷启动（缓存未命中，重建后单次采样）**

| 标记 | 相对进程启动 |
|---|---|
| payload 读入 / 解析 / 路径就绪 | 4.9 / 5.7 / 6.5 ms |
| 缓存未命中 | 7.0 ms |
| **解压完成（1,002 文件 / 33.6 MB）** | **335.3 ms**（解压本体 ~328 ms） |
| 校验 + 原子改名 + 写 marker | 360.5 ms |
| 清理旧版本 + 拉起 | 711.0 ms（其中 stat 校验 ~15 ms、旧版本扫描/删除 ~150 ms） |
| 外壳退出 | 783 ms |
| 窗口可见 | 1,540 ms（该次偏快；5 次中位 1,833） |

外壳退出后应用继续运行：外壳 `+66 ms`（热）/ `+783 ms`（冷）已退出，1.5 s 后应用进程数仍为 1。外壳未创建任何 Job，PE `subsystem=2`（无控制台），测量期间未出现控制台窗口。

版本身份不靠启动时哈希：payload 的 SHA256 在**构建期**算好并写进外壳常量，缓存目录名取前 16 位十六进制，所以热启动不需要读 15.6 MB 重新哈希。作为对照，实测 SHA256(payload 15.6 MB)=6.2 ms、SHA256(onedir 33.6 MB)=13.8 ms——即使每次全量哈希也只在 15 ms 量级，选择逐文件 stat（15.2 ms）主要是为了拿到逐文件粒度做自愈判断。

## 5. 成本归因：Defender A/B 做不了，用代偿实验

**Defender A/B 结论：无法执行。** 本机 Defender 未安装（证据见 §1），且当前非管理员，无法安装/加排除。因此"同一 onefile 在排除 vs 不排除"这一组数据**不存在**，不做伪造。

七组代偿实验/对照定位成本：

| 实验 | 结果 | 含义 |
|---|---|---|
| 建 1,002 个空文件 | 138 ms（0.14 ms/个） | 文件创建本身不贵 |
| 写 1,002 个文件 / 33.6 MB | 269 ms（项目盘 283 ms） | 上一轮"1.78 ms/entry ≈ 1.8 s"不成立 |
| 同一目录连续启动（温） | 269–348 ms | 基线 |
| 同一目录受控闲置 5 分钟后首启 | 316 / 286 ms | **没有"退冷"**；单发 1,864 ms 视为偶发干扰 |
| 同一份 onedir 拷到新目录后首启 | 1,547 / 1,099 / 1,808 ms | 新写/新拷文件的首次执行成本 ~1.1–1.8 s |
| Python 顺序读完全部 33.6 MB（刚拷完） | 65 ms（再读 61 ms） | 不是普通读 I/O 慢 |
| onefile bootloader（进程→Python） | 793 ms | 解压 + 第二次拉起 |

修正后的归因：onefile 的 ~1.8 s = 解压/bootloader ~0.8 s + **"1,002 个新文件的首次执行/加载"~1.0 s**。这 ~1.0 s 的稳定触发条件是"文件刚被写入或拷贝"：onefile 每次解压出一批新文件，fresh-copy 每次也付；而同一个目录第二次启动只 269–348 ms。它更像第三方文件系统过滤驱动（`QQSysMonX64`）对新文件的内容检查，或 Windows 预取/加载器状态对新文件的初始化，而不是"路径换了"。**非管理员无法进一步隔离**（不能停驱动、不能比较 Defender 排除），可以确定的是：

- A 的收益**不依赖 Defender**（本机没有 Defender，仍有这 ~1 s）；
- 受控 5 分钟闲置没有让热缓存退化（A 热 425/317、onedir 316/286），所以 A 的收益不是"几分钟就没了"；但出现过一次无法复现的 1,864 ms，说明背景扫描类事件会偶发打断热态，属于环境噪声，报告如实列出。

## 6. 缓存语义测试

| 场景 | 结果 |
|---|---|
| 删掉缓存里的 `_internal\tcl86t.dll` | **自愈**：检测到尺寸不符 → 重解压 → 窗口 1,311 ms，dll 恢复 |
| 删掉 `payload.marker` | **自愈**：重解压 → 窗口 1,417 ms |
| 同尺寸内容损坏（把 dll 前 64 KB 写 0） | **未检测到**（只比尺寸）→ 拉起后弹出 `Unhandled exception in script` 错误框（已抓窗口标题核实），不自愈 ← **缺陷** |
| 版本升级 v1 → v2（两个不同 payload 外壳） | v2 目录新建；v1 目录保留（作为"最近一个旧版本"）；v2 冷启 2,121 ms |
| 再升 v3 | v3 为当前，v2 保留，**v1 已删除**；v3 冷启 2,784 ms |
| 同时启动两个外壳 | 修复前起了 **2 个应用实例**（`FindWindowW` 匹配不到 Tk 窗口）；改用 `EnumWindows` + 标题匹配后：第二个外壳退出码 0，应用进程数保持 1 |
| 外壳退出后应用存活 | 存活（见 §4） |

## 7. 缺陷清单

| # | 缺陷 | 影响 | 修复成本估计 |
|---|---|---|---|
| 1 | 只校验文件尺寸，同尺寸内容损坏检测不到 | 缓存被静默改坏时应用报错而非自愈 | marker 里加每文件 CRC32/SHA256：热启动 +65 ms 读 + 15 ms 哈希 ≈ **+80 ms**（329→~410 ms）；或只校验 PE/DLL（~8 MB，+25 ms） |
| 2 | 冷启动仍 ~1.8 s，且窗口出现前无任何反馈 | 首次/升级后首启体验与现在一致甚至更"空" | 可选：解压后多线程预热（把 ~1 s 的应用首访税前置并并行）；未验证 |
| 3 | 偶发的 1.8 s 级背景事件（一次 onedir 1,864 ms；5 分钟受控闲置未复现） | 热启动偶尔被打回 onefile 水平；原因未定位（疑似第三方文件系统过滤驱动扫描） | 非管理员无法隔离；可先做异步预读/预热缓解，或接受 |
| 4 | 每版本 35.21 MB 磁盘，升级峰值 ~70.4 MB | 小硬盘用户敏感 | 可改"只保留当前"（省一半峰值，但回滚版本需重解压） |
| 5 | 构建非确定性（`tools\build_info.py` 嵌入 `datetime.now()`） | **同一版本重复构建会得到不同 payload 哈希 → 新缓存目录 → 旧缓存翻倍**，且"同版本升级"被当成新版本 | 缓存目录改用版本号 + marker 存 payload 哈希，或固定 `SOURCE_DATE_EPOCH` |
| 6 | 应用正在运行时旧缓存删不掉（文件占用） | 清理可能残留目录，不报错、不自愈 | 改为下次启动再清 / 只清非当前且非最近一个 |
| 7 | payload 追加在 PE 尾部 | 破坏 Authenticode；发布需"先签名后追加"或改用资源段 | 发布流程 0.5 人天 |
| 8 | 外壳无图标/版本信息/公司名 | 资源管理器观感差、易被误报 | 0.5 人天 |
| 9 | 硬编码 `DufsGui-v1.6.4.exe` 与 payload 哈希 | 每次发版必须重建外壳（哈希头由打包脚本生成，属预期） | 已脚本化，接入 CI 0.5 人天 |
| 10 | 单实例靠窗口标题匹配 | 应用处于错误对话框时标题不同，可能放过第二个实例 | 建议应用侧提供命名 mutex，外壳 `OpenMutex` 判断 |

## 8. 回退方式

1. **产物级**：`dist\DufsGui-v1.6.4.exe` 原样未动；A 产物只在 `_exp\`，不进入构建链。不发 A 就等于回退。
2. **用户级**：删除 `%LOCALAPPDATA%\DufsGui\payload\` 即彻底清除缓存；无注册表、无服务、无计划任务、无驱动。
3. **代码级**：外壳是单个 C 文件（`_exp\shell\dufs_shell.c`，~520 行）+ 打包脚本（`_exp\pack_payload.py`），与 Python 工程零耦合；`DufsGui.spec` / `build.bat` 未改。
4. **灰度**：可先只发 beta，或同时挂两个 exe，观察误报与缓存损坏投诉。

## 10. 方案 C 粗估（原生 C GUI + 只带 dufs 二进制，不写代码）

**可复用**
- 深色设计 token：`core/theme.py`（515 行）里的颜色/间距/圆角/字号常量 → 直接抄数值进 C 常量表（1 人天）。
- 二维码：`core/qr.py`（401 行）是纯算法（生成矩阵 + 掩码），可移植，或换一个小型 C QR 库（2–3 人天 / 1 人天）。
- 网页覆盖注入：`core/webtweak.py`（1,041 行）里的 JS/CSS 是字符串，可原样复用；要重写的是"注入通道"（HTTP 代理/响应改写）与生命周期（3–4 人天，重用率高）。
- dufs 二进制（3,464,192 B）与命令行参数策略、现有 207 项测试作为行为规格。

**判断**：A 用 ~0.5 人天把热启动做到 329 ms（冷启动无收益，偶发背景扫描会打断热态）；C 要 2 个月换来 ~10 MB 体积和"无 Python 运行时"，启动同样能到 150–250 ms。**现在不建议做 C**，除非明确要把"无 Python 运行时"作为产品目标。
